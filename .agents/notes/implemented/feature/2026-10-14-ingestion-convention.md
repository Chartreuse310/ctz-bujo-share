# Agent Note: ingestion-convention

Status: implemented

## Problem

用户给出了他的主要输入形式——一段自然语言（含开头 emoji 与正文 hashtag），以及四条 tag 处理期望：有相似 tag 就自动匹配、没相似就问、没打但内容合适就问、都没有就静默。核对后发现设计文档、原始想法、实现计划、AGENTS.md、运行时记忆里**没有任何一份描述过录入流程**：设计文档成功标准只写「在 content/ 下新增一个 Markdown 文件、跑一次构建」，它假设文件已经存在，从未规定文件怎么从输入变出来。同时这四条规则彼此有隐含冲突需要定界：规则①的「自动匹配」如果放宽成「相似匹配」，中文下会给出误导性建议（「绘画」与「书影音」编辑距离可能很近却毫无关系），反而比不提示更糟（用户会去改一个本来正确的值）；规则②③④则必须与既有 §11「新增 tag 必须先确认」保持一致。

## Decision

用户的主要输入形式是「一段自然语言 + 开头 emoji + 正文 hashtag」（例：`🏃 室内跑步 / 正文… / #跑步`），Agent 负责落成 `content/entries/YYYY-MM-DD-<slug>.md`。此前设计文档只规定了「文件长什么样」，从未规定「输入怎么变成文件」——录入层完全空白。现补齐为设计文档 §11.1，并在 AGENTS.md §5.5 复写要点（因为 AGENTS.md 是会话开始时自动加载的，必须有）。

四条 tag 规则（§11.1）：① 写了 tag 且与已登记项仅差**可机械判定**的等价（首尾/内部多余空白、全半角、英文大小写）→ 自动归一匹配，不打断；② 写了 tag 但无可机械判定的等价项 → 问用户「改用现有 tag 之一，还是新建」（新建须用户同意，遵守 §11 第 1 条）；③ 没写 tag 但内容明显适合某个**已登记** tag → 问是否加上；④ 没写 tag 也没有适合的 → 无事发生，不追问、不建议新建。

关键边界（负面保证）：**规则 ① 不得放宽为「相似」**。中文之下相似度无法可靠判定——「绘画」与「书影音」在编辑距离上可能很近却毫无关系；给出错误的「最接近」比不给建议更糟，因为用户会去改一个本来正确的值。因此只处理可确定的形态差异，其余一律走规则 ②。

hashtag 处理：正文里的 `#tag` 提取进 front matter 的 `tags`，**并从正文删除**（tag 只有 front matter 一处真相）。提取器**只认「井号后紧跟非空白字符」**——实测（marked）`#跑步` 与 `今天 #跑步 很爽` 都渲染成普通文字可安全提取，但 `# 跑步`（井号后有空格）会被渲染成 `<h1>跑步</h1>`，那是标题语法，不得当 tag 摘掉。

emoji 定位：开头 emoji（如 `🏃`）是用户习惯的前缀，**照原样保留**，不映射为 `type`、不剥离。它不是 §5.2 bujo 符号系统（`•`/`○`/`★`）的替代品，两套独立。

`type` 判定：由 Agent 按内容推断（发生的事 → `event`；想法/反思 → `thought`），**写入前告知用户判成了哪个**，用户可否决。不每条都问（每次录入多一轮往返），也不静默推断（判错会让统计计数错位且事后难发现）。

## Consequences

Cost: 录入层现在是一条新的、必须遵守的流程约定——它不像代码能自动执行，靠 Agent 每次读 AGENTS.md §5.5 与设计文档 §11.1 来遵守，因此是「靠纪律」而非「靠机制」。这是刻意的取舍：把 tag 抑制放在录入层，比放在构建层更能保住「增加有摩擦」的设计意图（§11 第 1 条）。Bought: 用户的自然语言输入有了确定的落档规则；四个分支里只有两个会打断用户，其余静默处理；hashtag 不会在页面上残留成一串死文字。

Follow-up obligations: ① §7 的近似匹配（D5）与「可复制的登记片段」两条仍未实现，降为第二道防线但**不能删**——它们防的是手改文件与 Agent 录错；② hashtag 提取器尚未实现，实现时必须只认「井号后紧跟非空白字符」，并为 `# 跑步`（会被渲染成 `<h1>`）写一条不提取的测试；③ 若日后发现 event/thought 推断频繁出错，需回到 §11.1 第 ④ 条改为让用户在输入里带类型信号。Named coverage gap: 本期没有任何机械校验能验证 Agent 是否遵守了这四条录入规则——它只能靠人工观察。
