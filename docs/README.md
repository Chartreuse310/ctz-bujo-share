# docs/ 文档地图（注册表）

> 本表是 `docs/` 各层**职责与真相源级别的唯一注册表**。新增文档前先看这里：一份内容只落一个地方，其余位置用纯文本路径互引，**不复述正文**。

## 分层

四层按**生命周期**排列，一层一个用途：

| # | 目录 | 阶段 | 回答什么问题 | 真相源级别 | 状态 |
| --- | --- | --- | --- | --- | --- |
| ① | [ideas/](ideas/) | 想法 | **想做什么**（需求从哪来、用户原话） | **不是**设计依据，仅作需求来源 | 已定稿 |
| ② | [specs/](specs/) | 设计 | **要做成什么样**（决策、数据模型、视觉、硬约束） | **唯一真相源**：与 ① 冲突时以它为准 | 已定稿 |
| ③ | [plans/](plans/) | 计划 | **怎么做**（任务、顺序、验证方式） | 施工依据，但需用户批准 | 已批准：否 |
| — | [ui-demos/](ui-demos/) | ② 的附件 | 视觉长什么样（可点的原型） | 原型，**不是**产品代码 | 已定稿 |

## 四层边界（防重复）

同一件事常常既出现在想法里、又出现在设计里。**按「谁说了算」归位，不要两处都写正文**：

- **想法** = 用户当时怎么说、为什么提这个需求；可以含**被放弃**的方向与原始设想。
- **设计** = 定稿结论 + 理由。**与想法冲突时以设计为准**——原始设想被推翻是正常的，不要在想法里"修正"它，那样会抹掉演进痕迹。
- **计划** = 把设计落成可执行任务；**不重新论证设计**，发现设计有问题要回到 ②。
- **原型** = 视觉的可点证据。demo 里的**假数据与缩写字段**（`h`/`ti`/`t`/`c`/`g`）不得搬进实现，以设计文档的全名字段为准。

## 为什么这样分层

- **`ideas/` 与 `specs/` 分开**：项目最初设想是「点阵纸 + 手写体」的 bujo 视觉，最终定稿却是「编辑体 + 细线底栏」——两者是**实质偏离**。若合成一份，这种偏离就看不出来了，后来人可能照原始设想"修正"回去。
- **`plans/` 不放在 `.agents/plans/`**：`plan` skill 的默认落点是 `.agents/plans/`，此处**有意偏离**。`.agents/` 在本仓库是运行时记忆区（`memory/` 被 gitignore），而计划是需要审阅、要入库、要长期留存的交付物——放进可能被忽略或清理的目录会误导后来人，也会让它游离于本表之外。
- **命名统一用「阶段」**：早先设计文档曾位于 `docs/superpowers/specs/`，`superpowers` 是上游 tooling 的品牌名，与本项目无关。改为 `docs/specs/`，四层同构（ideas / specs / plans / ui-demos），看名字就知道处于哪个阶段。

## 维护规则

1. **改设计先改 `specs/`**，再同步受影响的 `plans/`；不要在计划里私下改设计决策。
2. **新增一层前**先问：它能被归入现有四层之一吗？能就不要加层。
3. **路径改了要全仓库同步**——`node scripts/check-agents-md.mjs` 会校验 `AGENTS.md` 里引用的路径真实存在；改了 `docs/` 结构后务必跑一次。
4. **运行时记忆不入 `docs/`**：`.agents/memory/` 被 gitignore，其中值得留存的内容要**提炼进本目录**，不要依赖它。
