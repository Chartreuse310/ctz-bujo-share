## 1. 目标与成功标准

**要做什么**：一个公开的线上日记与思考分享站，把 bujo（Bullet Journal）的记录方式搬到 Web。一个**合并的月视图**（左侧月历网格 + 右侧当日/当月的列表分屏，月历固定可见、列表独立滚动）；首页是**今日日页**（当天日总结与全部条目 + 侧栏小月历与统计入口）；集子和 tag 是可浏览的入口；另有一页统计，按集子、tag、日期对比事件数与思考数。

**页面结构（已按 UI 定稿微调）**：四个可左右滑切换的视图，顺序固定为 **本月 | 今日 | 集子·标签 | 统计**，默认落在**今日**。导航已定稿为**底部通栏细线栏**（G1，见 §10、§12.6）。详见 5.2。

**给谁看**：完全公开，任何人拿到链接可访问。无登录、无权限、无后端。

**成功标准**

1. 在 `content/` 下新增一个 Markdown 文件、跑一次构建，就能在对应日期、集子页、tag 页、统计页看到它。
2. 月视图能一眼看出这个月哪些天有重点、是事件还是思考，同时右侧列表可通读当月内容；点某天能展开当天全部条目。
3. 统计页能回答「本月哪个集子写得最多」「某个 tag 逐月是涨还是落」。
4. 内容写错字段（比如 type 拼错、日期格式不对）在构建时**报错并指出文件**，而不是静默生成一个坏页面。

**明确不做（本期 YAGNI）**

- 在线编辑、账号、评论、RSS 之外的订阅分发
- 搜索（内容量小的时候用不上；留到有需要再加）
- 从 Obsidian 或其他外部库同步（已确认内容就放本仓库）
- 多语言、暗色模式之外的复杂主题系统
- 图片上传流水线（Markdown 里引用相对路径的图片即可）

## 2. 已确认的决策（来自讨论）

| 议题 | 决策 |
| --- | --- |
| 写作方式 | 本地 Markdown，构建成静态站 |
| 分享对象 | 完全公开 |
| 集子 vs tag | 集子**一对一**（像文件夹）；tag **多对多**（像关键词） |
| 事件 vs 思考 | 只是类型标记，字段完全相同；分开只为统计分别计数 |
| 日总结 | **独立类型**，一天一条，**不进主时间轴**，只在月历列表/日视图出现 |
| 统计重点 | 横向对比（集子/tag 之间）+ 纵向趋势（随时间） |
| 技术路线 | **Eleventy + 自定义脚本** |
| 内容位置 | **本仓库内** |
| 首页形态 | **今日日页**（当天日总结 + 全部条目），左侧固定侧栏含小月历与统计入口 |
| 月视图 | **一个合并视图**（原名两个：重点概览 + 月历列表）：左侧月历网格固定可见，右侧当月列表独立滚动；点列表中某天向左推进到该天日页。见 5.2 |
| 四屏导航 | 固定顺序 **本月 · 今日 · 集子·标签 · 统计**，可左右滑/方向键切换，不编号，默认选中「今日」。**位置已定稿**：底部通栏细线栏（G1，贴底 + 纸色封底），见 §10、§12.6 |
| 布局栅格 | 各页统一：次级栏 **236px**，栏间距 **56px**，主栏流体；页面元素一律不显示滚动条（仅月视图右列表可滚动）。**页面容器（2026-10-16 拍板）**：今日/集子·标签/统计/条目/日页统一 `.wrap`（max-width 1160px 居中、左右 40px），月视图用 `.shell`（同为 1160px 但用于分屏高度计算）——demo g1 原型即如此，实现不得遗漏外壳 |
| 重点标记 | 条目上的布尔字段 `highlight: true`，缺省 `false`。**手动标记**，系统不自动判定 |
| 视觉风格 | **已定稿：D 编辑体 + G1 细线底栏**（`docs/ui-demos/g1-line.html`）。米白纸面 + 衬线标题 + 朱红（`#a8321f`），底部通栏细线导航。原定稿瑞士墨线（方向 B）的约束（236px 栅格、发丝线密度、下划线重点标记、朱红只用于重点）在 D/G1 中均被继承。**均不得擅自调整既定设计，改动须与用户讨论**（详见 12.4、12.5、12.6） |
| 集子归属 | **默认不填 = 主集子**；只有长期大量记录的方向才单独立集子（现有：绘画、博士学位论文、书影音） |
| tag 增删 | **必须显式登记**，不做自动收录；手误不会变成分类页 |
| 显示名与 URL | **分离**：显示名可含中文/大小写/空格，slug 必须小写 + 连字符 |


## 4. 数据模型

### 4.1 条目（事件 / 思考）

`content/entries/` 下每个 `.md` 文件一条。文件名不影响语义（日期从 front matter 取），但约定用 `YYYY-MM-DD-slug.md` 便于人读。

```yaml
---
type: thought              # 必填，只能是 event | thought
title: 关于时间轴的想法      # 必填
date: 2026-10-14           # 必填，YYYY-MM-DD
highlight: true            # 选填，布尔；标为重点 → 进「本月」视图的左栏月历
order: 2                   # 选填，整数；同日内手动排序（见 §4.4）
collection: 博士学位论文     # 选填；不填 = 日常
tags: [PhD V2.0 P1.1, 播客]   # 选填，数组，可空；必须是已登记的 tag
---
正文，Markdown。
```

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `type` | 是 | `event` \| `thought` | 拼错即构建报错 |
| `title` | 是 | string | 非空 |
| `date` | 是 | `YYYY-MM-DD` | 决定在时间轴/月视图上的位置 |
| `highlight` | 否 | boolean | **重点标记**；缺省 = `false`。为 `true` 的条目进「本月」视图的左栏月历 |
| `order` | 否 | integer | **同日内手动排序**（2026-10-16 拍板，见 §4.4）；缺省 = 未设置 |
| `collection` | 否 | string | 一对一；**不填 = 日常**；必须是已登记的集子 |
| `tags` | 否 | string[] | 多对多；缺省 = 空数组；每个都必须是已登记的 tag |
| 正文 | 否 | Markdown | 允许为空（只有标题的条目） |

集子与 tag 都**按显示名引用**（写中文，不写 slug），由登记表解析成 URL。见 4.3。

### 4.2 日总结

`content/daily/` 下一天一个文件，文件名必须是 `YYYY-MM-DD.md`（日期是唯一键，从文件名取，**不在 front matter 里重复写**）。

```yaml
---
title: 今天想通了一件事   # 必填，月历列表上的「简述」用它
---
正文，Markdown。
```

**一天最多一条**：同名日期出现第二个文件（或 front matter 里另写日期）时构建报错。

### 4.4 同日条目的手动排序（`order`，2026-10-16 拍板）

**问题**：同一天的条目顺序原本由文件名字母序决定，用户无法控制。静态站没有运行时 UI 可拖拽，顺序必须落在内容文件里。

**方案**：条目 front matter 增加可选整数字段 `order`，语义：

- **只在同一天内比较**。别的页面（集子页、tag 页、统计、月视图当月列表）按日期倒序的既有规则**不变**，不受 `order` 影响。
- **排序规则**（`lib/load.js` 分组时执行）：同日内 → ① 有 `order` 的按**升序**排在最前；② 没写 `order` 的按**文件名序**跟在后面；③ `order` 相同按文件名序（稳定兜底，保证构建确定性）。
- **只提一条也要重排序号吗？不用**：只给想提前的条目写 `order: 1`，其余不写即可全部排到它后面。
- **缺省 = 未设置**，不是 0——避免「没写 order」与「明确写 order: 0」的语义混淆。
- 校验：非整数（如 `"2"`、`2.5`、`true`）= 构建报错（§7 口径）；是**已知字段**，不触发未知字段警告。

**已否决的替代**：日总结文件维护顺序清单（没写日总结的日子没有落点，且让日总结耦合条目信息）；文件名加序号前缀（改 slug = 改 URL，违反「改标题不影响 URL」的 §5.1 底线）。

### 4.3 分类登记表（taxonomy）

集子与 tag 都**不是**从条目里自动扫出来的，而是集中登记在一份文件里：

`content/taxonomy.yml`

```yaml
# 默认集子的显示名（URL 固定为 /collection/all/，不在这里配 slug）
default_collection_name: 日常

collections:
  - name: 绘画
    slug: drawing
  - name: 博士学位论文
    slug: phd-thesis
  - name: 书影音
    slug: books-films-music

tags:
  - name: PhD V2.0 P1.1
    slug: phd-v2-0-p1-1
  - name: 跑步
    slug: running
  - name: 吉他
    slug: guitar
  - name: 播客
    slug: podcast
  - name: 视频
    slug: video
```

> **关于 `PhD V2.0 P1.1` 这个 tag**：`name` 含空格、点号与原大写（合法——`name` 是自由文本），`slug` 用连字符替代非法字符得 `phd-v2-0-p1-1`（**slug 不得含点号**，正则 `^[a-z0-9]+(-[a-z0-9]+)*$`）。
>
> ⚠️ **已知代价（用户已知情并选定）**：设计规定 **slug 永久不变、改名只动 `name`**，所以将来推进到 V3.0 时，若要沿用同一个 tag 就**必须改 `name` 而保留旧 slug** `phd-v2-0-p1-1`——URL 会永远停在 V2.0 的字样；若每次升版都新建 tag，则 tag 会随版本持续膨胀（与 §11 第 1 条「克制地增加」的初衷相悖）。这是用户明确选择的取舍（备选方案是「tag 不带版本号，版本写进正文」被否决）。

**规则**

| 规则 | 说明 |
| --- | --- |
| 显示名与 URL 分离 | `name` 是给人看的（可含中文、大小写、空格）；`slug` 是 URL 用的，**必须小写字母 + 数字 + 连字符** |
| slug 格式校验 | 正则 `^[a-z0-9]+(-[a-z0-9]+)*$`；不合格即构建报错 |
| slug 唯一 | 集子之间、tag 之间各自唯一（集子与 tag 可以同名，因为 URL 前缀不同） |
| 条目按显示名引用 | 条目里写 `collection: 博士学位论文`、`tags: [PhD V2.0 P1.1]`，与 `name` 精确匹配（`name` 可含空格，故 YAML 里含空格的元素要加引号） |
| **未登记的引用 = 构建报错** | 写了一个登记表里没有的集子或 tag，构建中断并提示「未登记，若确认要新增请先加到 taxonomy.yml」 |
| **主集子** | 不写 `collection` 的条目归入主集子。主集子**不占用** slug，URL 固定为 `/collection/all/`，显示名取登记表的 `default_collection_name`（默认 **「日常」**），且**不可被删除** |
| 登记但未使用 | 允许。集子/tag 页照常生成，只是列表为空（保留空态文案） |

**为什么用登记表而不是自动扫描**

1. **URL 稳定**：显示名以后可以改（`书影音` → `书籍影视`），slug 不变，旧链接不失效。自动扫描做不到这一点。
2. **克制地增加 tag**：新 tag 必须显式登记，天然形成一道确认。自动扫描会让任何一次手误（`跑步 ` 带空格、`Runnning` 拼错）变成一个永久的分类页。
3. **零成本扩展**：以后要加 tag 描述、颜色、排序权重，都只是往这份表里加字段。

**新增 tag / 集子的流程**（这是唯一需要「确认」的动作）

1. 在 `content/taxonomy.yml` 里加一条，写 `name` 和 `slug`。
2. 在条目里按 `name` 引用。
3. 构建通过。

若条目里引用了未登记的 name，构建会失败并给出可直接复制的登记片段，避免你去翻文档查格式。

**slug 建议**（手写，不自动生成）

中文名没法机械转 slug，所以 slug **由你手写**，构建只负责校验格式和唯一性。登记表里已给的示例可作参考。若你希望我给一份「中文 → 英文 slug」的建议对照，我可以在实现时附一个提案文件，但**不会自动写入**。

### 5.1 条目详情的 URL（`/entry/<slug>/`）

条目的文件名是 `YYYY-MM-DD-<slug>.md`，其中 `<slug>` 部分**由你手写**，规则与集子/tag 一致：小写字母 + 数字 + 连字符。

```
content/entries/2026-10-14-read-a-book.md
                              └──────────┘ ← slug，手写
→ /entry/2026-10-14-read-a-book/          （slug 含日期，天然唯一）
```

- **slug 含日期前缀**：`/entry/2026-10-14-read-a-book/`。这样 slug 天然不重复，也不会因为同名而冲突；日期信息在 URL 里可见，便于人读。
- **文件名即 slug 来源**，不在 front matter 里重复写。若文件名不含合法的 slug 部分，构建报错。
- **改标题不影响 URL**：`title` 可以随便改，slug 不动，旧链接不失效。
- **`title` 与 slug 独立**：`title: 读完《XX》` 配 `slug: read-a-book` 是正常的，不要求对应。

> 若你嫌手写 slug 麻烦：也可以在 front matter 里显式写 `slug:` 覆盖文件名派生值。两种方式都支持，但同一文件不能既有合法文件名又写冲突的 `slug`（以显式 `slug` 为准，冲突时以显式值为准并给出提示）。

### 5.2 月视图（本月，合并分屏）

原设计的「重点概览」（月历网格）与「月历列表」（日总结列表）合并为**一个视图**，同一屏幕左右分栏，各司其职。

**左栏 · 月历网格**

**目的**：一眼看到这个月哪些天有重点。

- 形态：月历网格，7 列 × 5~6 行，**周一起始**（可配置）。
- **整个当月必须一次可见**：月历在视口内完整呈现，不随页面滚动（用等高网格行 + `min-height:0` 实现，窗口再扁也保持整月可见）。
- 每格显示：日期数字 + **该日重点条目的数量** + 重点条目的标题（截断到 1~2 条，超出显示「+N」）。
- **事件点用颜色区分重点与普通**（用户 2026-10-14 拍板，取代 demo 的「红=思考、黑=事件」）：当天**有重点条目**的格子显示**红点**（`--accent` 朱红），**只有普通条目**的格子显示**黑点**（`--ink` 墨色）。一眼扫过去，红色格子即重点日——与左栏「目的：一眼看到哪些天有重点」一致。类型信息（事件/思考）不在格子上区分，看统计页与日页。
- 没有重点的日子保持空白，保留呼吸感。
- 点格子进日页（不是弹窗），保证可分享、可深链。

**右栏 · 当月列表**

**目的**：通读这个月的记录。

- 形态：**列表**，按日期顺序（默认**倒序**，最近的在上；可配置）。
- 每一行：日期 + 标题（可点击进日页）+ 正文摘要（截断，默认 1~2 行）。
- **行间距（2026-10-16 拍板）**：以 demo `.dlrow` 为准——每行 `padding: 14px 0 13px` + 行底 1px 横线（`--rule`），**首行与列表头之间不得贴死**，横线上下留白与 demo 一致。
- **列表头（2026-10-16 拍板）**：文案为「日总结」+ 条数（右对齐），不再用「当月日总结」。

**标题区与翻月控件（2026-10-16 拍板）**

- 标题区：`2026 · 10` 衬线大字 + **统计行**（`日总结 N · 重点 N · 条目 N`，mono 11px 灰、间隔居右），数据构建时算出；不再显示「N 天有记录」em。
- 翻月控件：**无边框无背景**的灰色 mono 小字链接（上一月 / 回到本月 / 下一月），居右；与 demo 的描边按钮组不同——用户拍板去掉边框和背景。「回到本月」仅在查看非当月时显示。
- 图例：**「· 重点 · 条目」**两枚——红点 = 重点日、黑点 = 有普通条目，与月历格红黑点语义一致；demo 的「事件/思考」图例不恢复（2026-10-14 已拍板类型不在月历区分）。

**条目卡片摘要 = 三行排版截断**（用户 2026-10-15 拍板，取代「摘要第一个段落」旧约）：

- **渲染整篇正文**进卡片（不做段落挑选），CSS `line-clamp: 3` 把显示区压到**最多三行**——内容不足三行就显示实际行数（1 段 1 行的短条目就只显示 1 行），超过三行固定三行封顶、第 3 行末尾出现「…」。
- 拍板细节：① 段与段之间**不留空行间距**（三行内塞更多字）；② **跨段截断可接受**——第 3 行可以停在中间段落；③ 「全文 →」链接**只在内容真被截断时显示**（超过三行），短内容不显示。
- 技术口径：截断是**纯排版行为**（CSS），模板层不做任何段落选择；详情页 `/entry/<slug>/` 仍是全文。
- **行尾重点标记**（用户 2026-10-14 拍板）：当日有重点条目的日总结行，行尾显示**红色事件点**（`--accent` 圆点，即 demo `.cal-foot` 图例里的重点点），不显示黑色普通点——黑点表示「只有普通条目」，日总结行尾有黑点没有意义（日总结本身不是重点载体）。红点取代初版评审提的「★N 文本」方案，与左栏事件点同一视觉语言：**红 = 有重点**。
- **独立滚动**：右列表自己的滚动条（视觉上隐藏，用底部渐隐提示），滚动时左栏月历**纹丝不动**。
- 没有记录的日子不出现，避免大片空行。

**「重点」是手动标记**（已确认）。系统**不**自动判定重点——没有基于 tag、字数、集子的隐式规则。`highlight` 只能由你在 front matter 里写 `true` 决定。

> 格子里的**数量与符号**是构建时从 `highlight: true` 的条目里算出来的，不需要你手工维护任何月度索引。

**推进动效**：在右列表点某一天，视图**向左推进**到当天的日页（配合顶部四屏的方向感知推进动效，可反向划回）。

**bujo 符号系统**

| 符号 | 含义 |
| --- | --- |
| 红点（`--accent` 圆点） | 当天**含重点条目**（`highlight: true`）——月历格与右栏日总结行尾同一语义 |
| 黑点（`--ink` 圆点） | 当天**只有普通条目**——仅月历格使用，右栏不显示 |
| `×` | 已完成（本期不做完成状态，**符号先预留**） |
| `→` | 已迁移（同上，预留） |

> 用户 2026-10-14 拍板：**颜色语义 = 重点/普通**，取代 demo `g1-line.html` 的「黑=事件、红=思考」旧语义（当时红点实为思考标记）。类型信息（event/thought）不在月历格区分，看统计页与日页。原文本符号 `•`/`○`/`★` 不再用于月历渲染——`×`/`→` 仍为下一期预留。

## 6. 统计设计

统计在**构建时**算好，输出一份 JSON，页面用**手写内联 SVG** 画图（不引入客户端图表库：站点是静态的，图表数据在构建时就固定了，没必要为此加载几百 KB 的 JS）。

**统计页三块**

1. **总量卡片**：事件总数、思考总数、日总结数、有记录的天数、**重点条目数**。
2. **横向对比**：选定时间窗口（本月 / 本年 / 全部，可切换）内，按集子和按 tag 的条目数排行，横向条形图；每条同时显示事件数与思考数（堆叠或并列）。
   - 集子列表较长时显示前 N 个（默认 10）+「其他」。
3. **纵向趋势**：按月（本年）或按日（本月）的折线图，事件数与思考数两条线。

**「比较和变化」怎么体现**

- 横向：同一时间窗口内，集子/tag 之间的条目数差异（排行条）。
- 纵向：时间序列的涨落（折线）。
- 变化率：每个集子/tag 在「本期 vs 上期」的增减，用 ↑/↓ 加百分比标注。上期为 0 时显示「新增」而不是「+∞%」。

**口径**

- 计数单位是**条目**（一个 Markdown 文件算一条），不是字数。
- 日总结**不计入**事件/思考统计，单独计数（因为它是独立类型）。
- **重点条目仍计入**事件/思考总数（`highlight` 是附加标记，不改变条目本身的性质）；同时**额外**单独统计重点数。
- 日期归属一律用 `date` 字段，不用文件修改时间。

## 7. 校验与错误处理

构建时校验，失败就**中断构建**并打印 `文件路径 + 字段 + 实际值 + 期望值`。要覆盖：

| 情况 | 处理 |
| --- | --- |
| `type` 不是 `event`/`thought` | 报错 |
| `date` 格式非法或不存在（如 `2026-02-30`） | 报错 |
| `title` 缺失或空 | 报错 |
| `tags` 不是数组 / 元素为空字符串 | 报错 |
| `collection` 不是字符串 | 报错 |
| 两条记录的 slug 冲突（如两个文件都叫 `note.md`） | 报错 |
| 集子 / tag 的 slug 不符合 `^[a-z0-9]+(-[a-z0-9]+)*$` | 报错 |
| 集子之间（或 tag 之间）slug 重复 | 报错 |
| 登记表里 name 重复 | 报错 |
| 条目引用了未登记的集子 / tag | **报错**，并给出可复制的登记片段 |
| 条目引用集子/tag 时大小写或空格不精确匹配 | 报错，并提示最接近的已登记名称 |
| 日总结文件名不是 `YYYY-MM-DD.md` | 报错 |
| 同日两个日总结 | 报错 |
| `date` 为未来日期 | **允许**（不报错）。见下方说明 |

**关于未来日期**（已确认）：条目和日总结都**允许**写未来日期，系统不加限制、不报错、不提示。理由是写日记时可能提前规划或补记，未来日期的合理性由作者自己判断，不需要校验器越界。实现时**不要**加「日期不得晚于今天」之类的规则。
| 未知的 front matter 字段 | **警告**（不中断），提示可能是拼写错误 |
| `highlight` 不是布尔值（如写成 `"yes"`） | 报错 |
| `content/entries/` 为空 | 正常构建，页面显示空态文案 |

**校验实现**：用 **`zod`** 声明 schema（已确认）。手写校验器的成本主要在错误信息质量上，而错误信息正是这个项目「写错要立刻知道」的关键。本项目除 Eleventy 之外引入的依赖只有 **`zod`** 与 **`js-yaml`**（后者为解析 `taxonomy.yml` 所必需，见 §10 决策状态；Eleventy 不原生解析 `.yml`，实测确认）。

## 11. 协作约定（给未来的自己 / Agent）

这一节不是代码，是使用这套系统的规矩。落进仓库，避免以后忘掉。

1. **新增 tag 必须先确认**。Agent（或任何自动化）**不得**擅自往 `content/taxonomy.yml` 里加新 tag；需要新增时先向用户提议，用户同意后才写入。理由：tag 的克制是靠「增加有摩擦」维持的，自动化会毁掉这道摩擦。
2. **新增集子同理**，且门槛更高——集子是「长期大量记录的方向」，不是一次性主题。
3. **不自动生成 slug**。中文显示名到 slug 的转换由用户决定；Agent 可以给建议，但不静默写入。
4. **改显示名安全**。改名只动 `name`，`slug` 不动，已有链接不失效。这是登记表设计的核心收益，改名时务必遵守。
5. **条目只按显示名引用**，不写 slug。这样改名时条目文件不用动。

### 11.1 录入约定（原始输入 → 条目文件）

用户的主要输入形式是**一段自然语言**，形如：

```
🏃 室内跑步
本来想去学校，但阴云密布还滴水了，于是改为在跑步机练习。sigma直接记录不进去，但是同步了小米运动健康的记录，也不错。
#跑步
```

Agent 负责把它落成 `content/entries/YYYY-MM-DD-<slug>.md`。以下 ①~⑤ 条是**唯一需要用户确认的时机**（tag 四种情形 + 集子三种情形 + hashtag 提取 + type 判定），其余一律不打断。

**① tag 的四种情形**

| # | 情形 | Agent 的行为 |
| --- | --- | --- |
| 1 | 写了 tag，且与某个**已登记** tag 仅差**确定等价**的形态 | **自动归一后匹配**，不打断用户 |
| 2 | 写了 tag，但没有确定等价的已登记项 | **问**：改成现有 tag 之一，还是新建 → 新建需用户同意（§11 第 1 条） |
| 3 | 没写 tag，但内容明显适合某个**已登记** tag | **问**要不要加这个 tag |
| 4 | 没写 tag，也没有适合的已登记 tag | **无事发生**，不追问、不建议新建 |

**①′ 集子的三种情形**（对称于 tag，只看元数据行——行结构见下）

用户的固定写法：**集子写在最后一行的行首**；同一行有 tag 时写在 tag 之前：

```
🏃 室内跑步                          ← 第 1 行：标题（emoji 前缀照原样保留）
<正文…>                              ← 中间行：正文，不做任何元数据提取
博士学位论文 #PhD V2.0 P1.1          ← 最后一行：元数据行（行首集子 + 若干 tag）
```

| # | 情形 | Agent 的行为 |
| --- | --- | --- |
| 1 | 元数据行行首写了集子，且与已登记集子仅差**确定等价**的形态 | **自动归一后匹配**，不打断（与 tag 规则 1 同口径） |
| 2 | 行首写了集子，但没有确定等价的已登记集子 | **问**：改用现有集子，还是新建 → **新建集子门槛更高**（§11 第 2 条：集子是「长期大量记录的方向」） |
| 3 | 行首**没写**集子，但内容明显属于某个已登记集子 | **问**要不要归入（用户明确要求：忘记写时必须提醒） |
| 4 | 没写集子，内容也明显不属于任何集子 | **无事发生**——不填 `collection` 归入主集子「日常」，这是**合法默认值**，不是遗漏 |

> **「行首」的边界**：元数据行**第一个 token** 才是集子候选。`#PhD V2.0 P1.1 博士学位论文`（集子写在 tag 之后）**不是**行首，不提取——「集子在 tag 前」是用户的固定写法，倒序出现视为正文描述，保持原样。
>
> **正文不触发匹配**：正文里提到集子名（如「今天的绘画练习」）不算「写了集子」，规则 1 不适用。
>
> **规则 3 的「明显」**：与 tag 规则 3 相同——有合理把握才问，不每条都问；但**宁多问一次，不错归一个**：错归会在集子页与统计里多一个计数，比漏提醒代价高。

> **「确定等价」的定义（不要放宽）**：仅限**首尾/内部多余空白、全角半角差异、英文大小写**这类**可机械判定**的差异。理由：中文之下「相似」无法可靠判定——`绘画` 与 `书影音` 在编辑距离上可能很近却毫无关系，**给出错误的"最接近"比不给建议更糟**，用户会去改一个本来正确的值。因此规则 1 只处理可确定的情形；形态不同但无法确定等价时，一律走规则 2 问用户。
>
> **规则 1 与构建期校验的关系**：规则 1 在**录入时**就把差异抹平，所以 `跑步 `（尾部空格）这类输入根本不会进到文件里。设计文档 §7 的「大小写/空格不精确匹配 → 报错并提示最接近的已登记名称」是**第二道防线**，防的是手改文件、Agent 录错、以及将来别的输入路径——两者不重复，都要有。

**② hashtag 的处理**

正文里的 `#tag`（如 `#跑步`）**提取进 front matter 的 `tags`，并从正文删除**。这样 tag 只有一处真相（front matter），页面正文里不会残留一行 `#跑步`。

**判定「哪些 # 是 tag」用三条规则，按顺序应用：**

1. **只从「独立成行 / 行尾的元数据行」提取**，例如 `博士学位论文 #PhD V2.0 P1.1`。**正文行里的 `#` 一律不提取**（正文里的 `#` 保持原样，是内容的一部分）。元数据行的行首 token 是集子候选（见 ①′）。
2. **tag 从 `#` 延伸到下一个 `#` 或该行末尾**，因此一行可以写多个 tag，且 **tag 名里可以含空格**（如 `PhD V2.0 P1.1`）——这是必须的，因为 `name` 允许含空格（§4.3）。实测：`绘画 #跑步 #播客` → `["跑步", "播客"]`；`博士学位论文 #PhD V2.0 P1.1 #论文写作` → `["PhD V2.0 P1.1", "论文写作"]`。**「遇空格即止」是错的**，它会把 `#PhD V2.0 P1.1` 截成 `PhD`。
3. **`#` 后必须紧跟非空白字符**才可能是 tag；`# 跑步`（井号后有空格）不提取。

> ⚠️ **为什么必须限定「行」这个前提**：实测（marked）`#跑步`、`今天 #跑步 很爽` 都渲染成普通文字，可安全提取；但 **`# 跑步`（井号后有空格）会被 Markdown 渲染成 `<h1>跑步</h1>`**——那是标题语法，不是 tag，摘掉会吃掉手写的标题。
>
> 而「`#` 延伸到行尾」若不加限定地用在**正文行**上，`今天 #跑步 很爽，还聊了 #播客` 会被吞成一个 tag `跑步 很爽，还聊了 #播客`——明显错误。**因此规则 1（限定行）是规则 2（延伸到行尾）成立的前提，两者不可拆开使用。** 这也是本次实测发现的规则缺陷：初版只写了「井号后紧跟非空白」，无法表达含空格的 tag。

**③ 开头 emoji 的角色：保留，不作类型信号**

用户输入常以 emoji 开头（如 `🏃`）。它**是用户习惯的前缀，照原样保留在标题/正文里**，**不**映射为 `type`，也**不**剥离。

- emoji **不是** bujo 符号系统（§5.2 的 `•` / `○` / `★`）的替代品，两套符号各自独立。
- 因此**不能**由 emoji 推断 `type`。

**④ event / thought 的判定：Agent 推断 + 告知，用户可否决**

`type` 由 Agent 按内容推断（发生的事 → `event`；想法/反思 → `thought`），**写入前告知用户判成了哪个**，用户可否决并更正。

- 不采用「每条都问」——那会让每次录入都多一轮往返。
- 不采用「静默推断」——判错的代价是统计计数错位，且事后难发现。
- 如果将来发现推断频繁出错，再考虑让用户在输入里显式带类型信号。

### 12.2 视觉偏好

- **偏好窄次级栏 + 宽主栏**的编辑式栅格，基准是「集子·标签」页的 236/788。
- **标记强度要低**：倾向「细线 / 方框 / 淡底色」，忌讳高饱和标记。实测教训：方点距数字太近、红圈太跳都会被指出。
- **同元素多标记要能叠加**：「本日」与「选中」同日时互不覆盖（本日 = 灰框 + 淡灰底 + 加粗；选中 = 黑色内描边），两者同尺寸可同时显示。
- **重点标记用下划线**（不用方点）：灰线 = 有记录，朱红线 = 含重点，flex + 4px gap 固定间距。
- **朱红 `#d93a1f` 只用于重点与选中态**，不作他用。
- **数字一律等宽**（`tnum`）。
- **字体分工：标题衬线，小字无衬线**。衬线只给「标题级」——`h1`–`h4` 自身（≥14px）、大数字（日期 / KPI / 统计数，≥17px）、品牌字；其余一律无衬线。理由：小字号衬线（尤其中文）可读性差，且衬线一多就失去对比、衬线与无衬线的分工也跟著失效。字号分界取 **17px**。

| 字号 / 角色 | 字体 | 典型元素 |
| --- | --- | --- |
| ≥17px 的数字与大标题 | 衬线 | `.dateline b` 日期、`.kpi .n`、`.stat-pair .p .n`、`.head h1`、`.month-top h1`、`.cell .num` |
| `h1`–`h4`（≥14px） | 衬线 | `.pull h2`、`.entry h4`、`.dlrow h4`、`.card h3`、`.res-head h2`、`.resrow .t`（条目标题） |
| <17px 的小字、眉题、标签、正文摘要 | 无衬线 | `.kicker`、`h1` 内 `<em>` 眉题、`h3` 区块眉题、`.cell .cap`、`.dlrow p`、`.list-empty`、`.head .aside`、`.rank-row .nm`、`footer.note`、`.resrow .t .sub`、`.entry .idx` |
| UI 控件 | 无衬线 | 顶栏 / 底部导航按钮、`.mini-head`、`.seg`、`.pager`、`.tag` |

> 原为「斜体衬线」的小字标签（`.kicker`、`.entry .idx`、`h1` 内 `<em>`）改无衬线时**一并取消斜体**——中文斜体是伪斜，发虚。

### 12.3 验证方法（可复用）

验证「不滚动 / 不裁切」这类硬约束时，**不要靠肉眼看截图**，要用 headless Chrome + CDP 实测：

- 量 `documentElement.scrollHeight/clientHeight`（页面是否产生滚动）
- 量格子 `scrollHeight > clientHeight`（内容是否被裁切）
- 量 `getBoundingClientRect` 位移（左月历在右列表滚动时是否位移为 0）

**悬浮元素必须做「元素级遮挡检测」**：底部导航、方向切换条这类 `position:fixed` 元素，只看容器矩形会漏判——实测发现，容器级检测（`navRect.top < calPane.rect.bottom`）曾判 TRUE 却未指出被压的是哪个元素。正确做法是遍历目标区域内**每个可见元素**的矩形与悬浮矩形求交（`ix = min(right)-max(left)`、`iy = min(bottom)-max(top)`，两者均 >0 即遮挡），输出被压元素的类名与文字，才能定位到「月历图例被压 13px」这种具体问题。本次 G 就是这样查出并修掉的（见 12.5）。

**贴底元素不能测「下方有无内容」，要测「导航带内的命中」**：G1 通栏贴底后 `nav.bottom === innerHeight`，视口底边之下没有区域，「有没有内容漏在底栏下方」按定义恒为假——这种断言测了等于没测（早期版本正是这样，`gap=0` 时直接跳过检查）。正确口径是**采样点遮挡检测**：在导航带内按网格取点（x 每 37px、y 每 4px），每点 `elementFromPoint`，断言命中 `.tabbar` 或其按钮、绝不命中内容元素，并断言导航底色不透明。G1 实测 5 档视口 × 4 屏 × 5 个滚动位置，2145~2860 点零穿透（脚本 `.agents/occl-g1.mjs`）。

**还要测「底栏抬高」这条路径**：G1 的穿帮不是它自己写错，而是共享块 `shortViewportG()` 里一条给 G0 的 `.tabbar{bottom:12px}` 覆盖了它的贴底声明——`max-height:760px` 才触发，所以只在矮视口复现。教训：**共享的矮视口/响应式块不得写死某个皮肤的定位属性**，且验证必须覆盖 `@media` 断点两侧（760 / 761px）与多个滚动位置。

**只测「有数据的状态」会漏检**：月历格定位右侧列表的实测里，曾误取上个月（9 月）的格子，而右列表只含当月日总结，导致 `scrollTop` 恒为 0、看起来像功能坏了。测交互要先用 `#mToday` 回到当月、取列表里位置最深的一行，再验证 `scrollTop` 真实变化。同理，深链格式是 `#stats` 而非 `#s-stats`；触滑必须派发真实 touch 事件（`Input.dispatchTouchEvent`）并开启 `Emulation.setTouchEmulationEnabled`，用 `Input.dispatchMouseEvent` 拖拽不会触发。

**别把既有动画的瞬时值当溢出**：切屏动画 `pushFromRight` 会让 `.screen.on` 有 `translateX(36px)`，动画期内 `scrollWidth` 会临时大于 `clientWidth`（实测 1476 vs 1440，800ms 后归位）。测横向溢出必须等动画（.28s）结束再测，否则会把正常动画报成缺陷。

已知坑：`file://` 下 Chrome 对同路径不同 query 的截图可能命中缓存，导致「截图没变」误判。判断是否生效**以 `getComputedStyle` 为准**，截图前必须 `Network.setCacheDisabled`。

### 12.6 G 底栏的「重量」变体

**起因**：用户反馈 G 的深色胶囊底栏「太重」。诊断——深色实底 + `backdrop-filter` + 外阴影 + 朱红整块填充，四项重量叠加，使底栏成为界面里最抢眼的元素，与编辑体「纸面 + 发丝线」的克制调性冲突。

**做法**：在**同一界面逻辑**下出 5 个不同重量的皮肤（`docs/ui-demos/g1-line.html` ~ `g5-slim.html`），与 G 原版（`g-bottom.html`，下称 G0）共 6 份横向对比。生成脚本 `scripts/gen-ui-demos.mjs` 里的 `navSkins` 块**只覆盖 `.tabbar` 与 `.tabbar button` 的视觉**，位置基准、层级、`--tab`(52px) 底部预留、DOM 结构与交互全部不动，所以 6 份的界面逻辑逐字一致，D/E/F 零变化。

| 文件 | 方案 | 形态 | 当前态标示 | 重量 |
| --- | --- | --- | --- | --- |
| `g-bottom.html` | G0 · 深底胶囊 | 深色实底 + 阴影 + 毛玻璃，朱红整块 | 整块朱红 | 最重（原版） |
| `g1-line.html` | G1 · 细线栏 | 通栏发丝线，无容器 | 墨色 + 朱红下划线 | 很轻 |
| `g2-text.html` | G2 · 纯文字 | 无容器、无底线，四个词排在纸面上 | 朱红 + 600 | 最轻 |
| `g3-pale.html` | G3 · 浅底胶囊 | 纸面白底 + 发丝边 + 极淡阴影 | 淡朱红底 + 朱红字 | 轻 |
| `g4-quiet.html` | G4 · 极简 | 小字号 + 大字距，无容器 | 墨色 + 上方朱红圆点 | 最轻 |
| `g5-slim.html` | G5 · 窄条 | 保留深色，但更窄更扁更透、阴影更淡 | 整块朱红 | 中等（折中） |

6 份全部通过四档视口的 §12.1 硬约束与 §12.5 底部导航约束；交互（四屏点击 / 键盘 ←→ / 触滑 / 深链）与侧栏可点性复验均无回归。**G1 通栏**要额外看一项：它横贯整个视口，实测未挡住小月历或内容点击（`elementFromPoint` 复验）。

**定稿：G1 细线栏**（用户：「G1 细线 效果最好」）。实现基线 = **D 的视觉 + G1 的底栏**。

**G1 的通栏贴底约束**（`g1-line.html`）

G1 与其余 5 个皮肤有一个本质差别：**它通栏且贴底**，底边就是界面边界；其余皮肤是浮动胶囊，药丸下方本就透出内容。所以只有 G1 需要保证「栏下不漏任何内容」：

| 项 | 值 / 做法 |
| --- | --- |
| 贴底 | `bottom:env(safe-area-inset-bottom,0px)`（不写 `bottom:0`，给 iPhone 安全区留位）；`height:calc(var(--tab) - 8px)` |
| 通栏 | `left:0;right:0;transform:none`（必须显式写 `none`，否则与基类的 `left:50%`+`translateX(-50%)` 叠加会整体偏移） |
| 封底 | `.tabbar::after`：`top:100%`、纸色 `var(--bg)`、`height:calc(24px + env(safe-area-inset-bottom,0px))`、`pointer-events:none` |
| 底线 | `border-top:1px solid var(--rule-2)`，无圆角 / 无阴影 / 无毛玻璃 |

> ⚠️ **`.tabbar` 的 `bottom` 只能由各皮肤自己声明，不得写进共享的 `shortViewportG()`**。该块排在所有皮肤之后，同特异性下会覆盖皮肤自己的位置声明——它曾经写着给 G0 用的 `.tabbar{bottom:12px}`，把贴底的 G1 抬离底边 12px，`max-height:760px` 的视口下滚动内容就从那道缝漏出（实测 600/640/700/720/744/760 六档全部命中，如「恢复跑，五公里」）。G0 的矮视口位置现由 `navSkins.deep` 单独负责。

**验证方法更正：`gap=0` 时「下方泄漏」口径失效，改用遮挡检测**

G1 贴底后 `nav.bottom === innerHeight`，视口底边之下没有区域，此时「有没有内容漏在底栏下方」按定义恒为假——测了等于没测。正确口径是**遮挡检测**：在导航带内按网格采样（x 每 37px、y 每 4px），每个点做 `elementFromPoint`，断言命中 `.tabbar` 或其按钮、绝不命中内容元素，并断言导航底色不透明。脚本 `.agents/occl-g1.mjs`，覆盖 5 档视口 × 4 屏 × 5 个滚动位置。

**G1 最终实测**：5 档视口（1440×900 / 1280×800 / 1440×700 / 1440×640 / 1920×1080）× 4 屏全部 `gap=0` 贴底，导航带内 2145~2860 个采样点全部命中导航、零内容穿透、底色不透明；长页末行净距 36px（`footer.note` 底边 820 / 导航顶边 856），无永久遮挡。

**取舍**（供定稿参考，不是结论）

- G1/G2/G4 重量最轻，与编辑体最协调；代价是「当前在哪一屏」的辨识度下降——G2 只靠朱红文字，G4 要靠圆点，弱于 D 顶栏的下划线，更弱于 G0 的朱红块。
- G3 是「仍是控件、但不压纸面」的折中：保留了胶囊的可点区域感，视觉重量约比 G0 降一半。
- G5 适合「想留深色身份但嫌 G0 太沉」的选择。
- 若最终仍选 G0，则 §12.2 的「标记强度要低」「忌讳高饱和标记」两条偏好需要为用户这条反馈开例外，并在文档记录原因。

## 13. 部署与每日重建（2026-10-15 拍板，D7 方案 A）

**托管**：GitHub Pages。仓库推 GitHub **公有** remote（内容本来就要公开；docs/ 设计文档随仓库一并公开，已确认接受）。

**每日重建**：GitHub Actions 定时工作流（`.github/workflows/deploy.yml`）：

- 计划：`cron: "0 21 * * *"`（UTC 21:00 = 北京 05:00，选凌晨是因为条目多为当天或前一天写，凌晨重建保证早上打开就是新的）。
- 步骤：`npm ci` → `npm test`（坏内容让部署失败而不是把坏站点发出去）→ `npm run build` → 部署 `_site/` 到 Pages（官方 `actions/upload-pages-artifact` + `actions/deploy-pages`）。
- **cron 不保证准点**（高峰可延迟数十分钟），对「今日」页可接受；未到点时展示的是前一次构建的结果，不是错误。
- 除定时外，**push 到主分支也触发同一工作流**——写完内容推送即发布，不等 cron。

**今日页的正确性边界**：「今日」由构建时刻的本地日期决定（构建机 UTC，`site.js` 已按本地时区计算）。每天至少一次 cron 重建是「今日页不冻结在昨天」的充要条件；两次构建之间站点内容不变，这是静态站的定义而非缺陷。

**安全边界**：工作流只用 `permissions: contents: read, pages: write` 最小权限；不使用任何 secret（纯静态构建无密钥需求）。内容校验失败（§7）时 `npm test` 退出非零、部署中止——坏数据永远不会被发布，只会让当天部署红掉并邮件通知。

**不做**：自定义域名（要买域名，以后再说）、预发环境（单人站没有多环境需求）、构建通知以外的监控。
